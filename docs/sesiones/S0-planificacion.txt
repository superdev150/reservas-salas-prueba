  La decisión central: cómo garantizar "sin choques"

  Este es el punto que más pesa, y la solución tiene que estar en la base de
  datos, no en el código de la aplicación.

  - Si la API primero comprueba que el hueco esté libre y después inserta, dos
    peticiones simultáneas pueden pasar las dos la comprobación antes de que
    ninguna inserte. Eso es justo lo que pasa hoy con el Excel.
  - Propuesta: PostgreSQL con una restricción de exclusión:
  EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH
  &&)
  WHERE (status = 'active')
    - Es atómica. Con 2 o con 50 peticiones simultáneas, Postgres deja entrar
      solo una y las demás fallan con el código 23P01, que la API traduce a 409
      Conflict.
    - El rango [) permite reservas seguidas: una de 10:00 a 11:00 y otra de
      11:00 a 12:00 no chocan.
    - El WHERE status='active' hace que una reserva cancelada libere el hueco
      sin borrarla.
  - Cómo se demuestra: un test que lanza unas 20 peticiones iguales a la vez.
    Debe dar exactamente un 201 y diecinueve 409. Ese resultado es la evidencia
    principal del cierre.

  Por esto la base de datos que propongo es PostgreSQL. SQLite o MySQL no tienen
  restricciones de exclusión por rangos y obligarían a usar bloqueos en la
  aplicación, que son más frágiles y más difíciles de explicar.

      293 +### 8.1 Carrera "desactivar sala" vs "crear reserva" (R12, D-2
          +6)                                                            
      294 +                                                              
      295 +**Problema:** sin bloqueo, una reserva puede validar `is_activ
          +e = true`, RRHH desactiva la sala y cancela las reservas futur
          +as **que ya ve**, y después se confirma la reserva nueva: qued
          +a activa en una sala inactiva. La FK de `bookings.room_id` no 
          +lo evita, porque solo toma `FOR KEY SHARE`, que no choca con u
          +n `UPDATE` de `is_active`.                                    
      296 +                                                              
      297 +**Solución:** ambas operaciones bloquean la misma fila de `roo
          +ms` con modos incompatibles.                                  
      298 +                                                              
      299 +*Crear reserva* (`POST /api/bookings`), una transacción en `RE
          +AD COMMITTED`:                                                
      300 +```sql                                                        
      301 +BEGIN;                                                        
      302 +SELECT id, is_active FROM rooms WHERE id = $roomId FOR SHARE; 
          +  -- no existe → 404; is_active = false → 422 ROOM_INACTIVE (R
          +OLLBACK)                                                      
      303 +INSERT INTO bookings (...) VALUES (...) RETURNING *;          
          +  -- 23P01 → 409 BOOKING_CONFLICT (ROLLBACK)                  
      304 +COMMIT;                                                       
      305 +```                                                           
      306 +                                                              
      307 +*Desactivar sala* (`PATCH /api/rooms/:id` con `isActive: false
          +`), una transacción:                                          
      308 +```sql                                                        
      309 +BEGIN;                                                        
      310 +SELECT id FROM rooms WHERE id = $id FOR UPDATE;               
          +  -- no existe → 404                                          
      311 +UPDATE rooms SET is_active = false, ... WHERE id = $id;       
      312 +UPDATE bookings SET status = 'cancelled', cancelled_at = now()
          +, cancelled_by = $adminId                                     
      313 + WHERE room_id = $id AND status = 'active' AND starts_at > now
          +();   -- rowCount = cancelledBookings                         
      314 +COMMIT;                                                       
      315 +```                                                           
      316 +(Cualquier `PATCH` de sala usa el `FOR UPDATE`, aunque solo ca
          +mbie el nombre: un único camino de código.)                   
      317 +                                                              
      318 +**Por qué funciona:**                                         
      319 +- `FOR SHARE` y `FOR UPDATE` son incompatibles. Si la reserva 
          +bloqueó primero, la desactivación espera a que la reserva term
          +ine y después la ve y la cancela. Si la desactivación bloqueó 
          +primero, la reserva espera y, al continuar, PostgreSQL le devu
          +elve la versión ya confirmada de la fila (`is_active = false`)
          +, así que responde 422 `ROOM_INACTIVE`.                       
      320 +- `FOR SHARE` es compatible consigo mismo: varias reservas de 
          +la misma sala siguen en paralelo, y el choque entre ellas lo r
          +esuelve la restricción (§8).                                  
      321 +- El orden de bloqueo es siempre "sala primero", así que no ha
          +y interbloqueos entre estas dos operaciones.
